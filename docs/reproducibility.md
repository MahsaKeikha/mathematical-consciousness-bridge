# Reproducibility Guide

This page is the practical entry point for reproducing the **Mathematical Consciousness Bridge** repository from a fresh clone. It covers installation, tests, linting, figure generation, repository-integrity checks, and GitHub Actions.

The goal is simple: a reader should not have to guess which commands were used to validate the mathematics or produce the generated visual atlases.

---

## 1. Supported environment

- **Python:** 3.10, 3.11, or 3.12
- **Primary test framework:** `pytest`
- **Static checks:** `ruff`
- **Numerical/figure dependencies:** `numpy`, `matplotlib`
- **Package installation:** editable install from `pyproject.toml`

The continuous-integration matrix runs the main test suite and Ruff on Python **3.10, 3.11, and 3.12**.

---

## 2. Fresh-clone setup

```bash
git clone https://github.com/MahsaKeikha/mathematical-consciousness-bridge.git
cd mathematical-consciousness-bridge
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

The `dev` extra contains the dependencies needed for tests, linting, and the generated figure atlases.

If your system provides `python3` rather than `python`, substitute `python3` in the commands below.

---

## 3. One-command verification

On systems with `make`:

```bash
make check
```

This runs:

```bash
python -m pytest
python -m ruff check .
python scripts/generate_all_figures.py --validate-only
python scripts/verify_repository.py
```

The direct commands are the canonical fallback when `make` is unavailable.

---

## 4. Run the full tests

```bash
python -m pytest
```

The test suite covers theorem implementations, exact witnesses, numerical certificates, dominance relations, finite-sample logic, figure geometry/content guards, publication integration, and regression behavior.

Useful pytest variants:

```bash
# concise output
python -m pytest -q

# run one theorem family
python -m pytest tests/test_projection_event_model_separation.py

# run one test by name
python -m pytest -k strict_improvement
```

A passing test suite confirms that the declared implementation and regression checks pass. It is **not empirical evidence** that the physical-to-experiential bridge has been established.

---

## 5. Run static checks

```bash
python -m ruff check .
```

Or:

```bash
make lint
```

Ruff checks the Python source, scripts, and tests according to the repository configuration in `pyproject.toml`.

---

## 6. Generate the reproducible figure atlases

Use the unified command:

```bash
python scripts/generate_all_figures.py
```

Or:

```bash
make figures
```

This runs both canonical computational generators:

```text
scripts/generate_quantitative_atlas.py
    -> docs/figures/quantitative/

scripts/generate_quantum_foundations_atlas.py
    -> docs/figures/quantum/
```

It then validates the complete SVG figure tree.

### Figure provenance matters

The repository intentionally contains **two kinds of visual assets**:

1. **Generated quantitative figures.** These are produced by numerical scripts from explicit equations, deterministic examples, or fixed-seed simulations. Their manifests live beside the generated SVGs.
2. **Source-controlled theorem and architecture figures.** These are publication diagrams used to communicate theorem structure, assumptions, inequalities, dependency, and scientific boundaries. They are vector source assets stored directly in `docs/figures/` and are validated rather than silently regenerated by an unrelated plotting script.

A theorem diagram should not be mistaken for simulated evidence, and a simulation should not be mistaken for a theorem. The [Figure Catalog](figure_catalog.md) and figure captions preserve that distinction.

---

## 7. Validate figures without regenerating them

```bash
python scripts/generate_all_figures.py --validate-only
```

Or:

```bash
make figures-check
```

The validator checks that:

- the quantitative manifest matches the quantitative SVG set;
- the quantum manifest matches the quantum SVG set;
- all SVG files under `docs/figures/` are valid parseable vector documents;
- no generated manifest silently points to a missing figure.

---

## 8. Verify repository publication consistency

```bash
python scripts/verify_repository.py
```

Or:

```bash
make verify
```

This checks reader-facing and publication-level consistency that is broader than an individual theorem unit test. Among other checks it verifies:

- the current release/version markers agree;
- the documented theorem frontier is P81;
- proposition proof files P1 through P81 are present exactly once;
- core reader and reproducibility documents exist;
- key local Markdown links resolve;
- package source and test modules are present;
- the test and figure GitHub Actions workflows exist.

The repository verifier is deliberately network-free so it can run in CI and in a fresh clone.

---

## 9. GitHub Actions: see the results without installing locally

The repository exposes two primary validation workflows.

### `tests`

Runs on pushes and pull requests using Python 3.10, 3.11, and 3.12:

```text
install package + dev dependencies
-> pytest
-> ruff
-> repository consistency verification
```

Open the repository's **Actions** tab and select the `tests` workflow to inspect the run matrix, individual steps, and failures.

### `figures`

The figure workflow can run automatically when figure-generation code changes and can also be launched manually with **Run workflow**. It:

```text
installs the project
-> regenerates both computational atlases
-> validates the complete figure tree
-> runs repository verification
-> uploads the generated atlas directories as a downloadable workflow artifact
```

This lets a reviewer reproduce and inspect generated outputs without writing into the repository.

## 11. Interpreting a successful run

A green test or figure-generation run means the **repository's formal and computational checks completed successfully** under the declared environment. It does not mean:

- every modeling assumption is empirically true;
- a latent target has been identified with consciousness;
- a non-rejected model has been validated;
- a quantum description has been shown to be experiential;
- the physical-to-experiential bridge has been solved.

The repository deliberately keeps **software reproducibility**, **mathematical proof**, **model adequacy**, **empirical evidence**, and **ontological interpretation** separate.

---

## 12. Recommended audit sequence for external reviewers

For a result you want to scrutinize closely:

1. read the proposition file;
2. read its equation/provenance record when available;
3. inspect the implementation in `src/consciousness_bridge/`;
4. inspect the corresponding tests;
5. run the focused test file;
6. run `make check` or the direct equivalent;
7. inspect the theorem figure and the [Figure Catalog](figure_catalog.md);
8. verify that the proposition's scientific-boundary statement matches the conclusion you intend to draw.
